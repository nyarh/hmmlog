정수 목록을 정렬한 뒤 특정 값을 찾는 코드를 직접 작성하면, 빈 목록과 마지막 원소의 처리까지 확인해야 한다. 표준 라이브러리에 맞는 함수가 있다면 정렬과 검색의 구현·검증 일부를 맡길 수 있다.

P.12, P.13, ES.1, SL.1, SL.2는 라이브러리와 도구를 활용하도록 권한다. 점수 목록을 정렬하고 검색하는 예제로 사용 조건과 검사 범위를 살펴본다.

## 코드에 작업 이름을 남긴다

다음 프로그램은 점수 목록을 정렬하고 42가 있는지 확인한다.

```cpp
#include <algorithm>
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> scores{42, 17, 65, 42};
    std::ranges::sort(scores);

    for (const int score : scores) {
        std::cout << score << ' ';
    }
    std::cout << '\n';

    const bool found = std::ranges::binary_search(scores, 42);
    std::cout << std::boolalpha << "found=" << found << '\n';
}
```

출력은 다음과 같다. 첫 줄의 마지막 점수 뒤에도 코드에서 출력한 공백이 하나 있다.

```text
17 42 42 65
found=true
```

`std::vector`는 원소를 담고 필요한 메모리를 관리한다. `std::ranges::sort`는 정렬, `std::ranges::binary_search`는 정렬된 범위에서의 존재 여부 확인이라는 작업을 드러낸다. `std::ranges`를 사용하는 이 예제에는 C++20이 필요하다.

호출하는 코드를 읽을 때는 정렬 알고리즘 내부의 인덱스 이동까지 따라갈 필요가 없다. 무엇을 정렬하고 찾는지 함수 이름으로 확인할 수 있다. ES.1과 SL.1은 이렇게 이미 이름 붙은 작업을 라이브러리로 표현하도록 권한다.

## 함수의 사용 조건까지 맡길 수는 없다

`binary_search`를 사용하려면 검색 조건에 맞게 범위가 정리되어 있어야 한다. 예제에서는 기본 비교 기준으로 전체를 정렬했기 때문에 그 조건을 만족한다. 정렬을 빼거나 다른 비교 기준으로 정렬했다면 같은 검색 호출을 그대로 사용해도 되는지 다시 확인해야 한다.

입력 조건을 만족시키고 객체 수명을 지키며 반환값을 처리하는 일은 호출하는 쪽이 맡는다. 라이브러리 내부 구현이 검증되었어도 이 조건을 어기면 결과를 신뢰할 수 없다.

한 번만 검색한다면 정렬 없이 순서대로 찾는 편이 알맞을 수도 있다. 검색 횟수, 원래 순서를 유지할 필요, 정렬 비용을 따져 고른다. 예제는 정렬과 검색을 연결하는 방법을 보여주며, 두 방식의 성능 우위를 측정하지는 않았다.

## 표준 라이브러리부터 살펴본다

SL.2는 표준 라이브러리를 우선 살펴보도록 권한다. 프로젝트에 참여하는 사람이 이미 사용법을 알고 있을 가능성이 높고, C++ 환경에서 공통으로 사용할 수 있는 구성요소이기 때문이다.

표준 라이브러리에 기능이 없으면 잘 관리되는 다른 라이브러리를 검토한다. P.13은 필요한 기능과 문서, 유지보수 지원을 갖춘 라이브러리를 활용하도록 권한다. 가져오는 코드의 양만으로 유용성을 판단하기는 어렵다.

사용 여부를 정할 때는 다음을 확인하면 좋다.

- 필요한 동작과 오류 처리 방식이 문서에 분명하게 나와 있는가.
- 프로젝트의 컴파일러와 표준 버전, 배포 환경에서 사용할 수 있는가.
- 할당, 지연 시간, 의존성처럼 프로젝트에 중요한 제약을 만족하는가.
- 업데이트와 문제 해결을 맡을 유지보수 기반이 있는가.

동적 할당이 제한된 환경에서는 크기가 변하는 컨테이너를 사용하기 어려울 수 있다. 고정 크기 저장소와 표준 알고리즘을 조합하는 등 프로젝트의 제약에 맞는 구성을 살펴본다.

## 반복해서 확인할 일은 도구에 맡긴다

P.12는 적절한 도구 활용을 권한다. 이 연재에서 가장 먼저 사용하는 도구는 컴파일러다. 문법과 타입 오류뿐 아니라 일부 의심스러운 사용도 경고로 확인할 수 있다.

예제 프로그램을 `library_example.cpp`로 저장하면 다음 명령으로 빌드하고 실행할 수 있다. Linux의 GCC 14.2.0에서 확인했다.

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -Wconversion library_example.cpp -o library_example
./library_example
```

`-std=c++20`은 언어 표준을 선택하고 나머지 옵션은 GCC의 경고 범위를 넓힌다. `-Wall`도 모든 경고를 활성화하지는 않는다. 경고 없이 빌드됐더라도 입력 조건이나 업무 규칙은 별도로 확인해야 한다.

도구별로 확인하는 대상을 구분하면 검사 결과를 해석하기 쉽다.

| 방법 | 확인에 도움이 되는 것 | 남는 확인 사항 |
| --- | --- | --- |
| 컴파일러 오류와 경고 | 문법·타입 문제와 일부 의심스러운 표현 | 입력 조건과 업무 규칙 |
| 정적 분석 | 도구가 구현한 규칙 위반과 위험 패턴 | 지원하지 않는 규칙과 진단의 문맥 |
| 실행 테스트 | 선택한 입력에서의 결과와 오류 처리 | 실행하지 않은 경우 |
| 코드 리뷰 | 설계 의도, 경계, 프로젝트의 제약 | 사람이 놓치기 쉬운 반복 검사 |

Core Guidelines의 일부 규칙은 정적 분석 도구로 검사할 수 있다. 도구마다 지원하는 규칙이 다르고, 진단이 실제 오류인지 문맥을 보고 판단해야 한다. 구체적인 도구 사용은 119편에서 다룬다.

## 작은 입력에서도 기대한 동작을 확인한다

앞 프로그램에서는 기본 목록 외에도 빈 목록, 원소 하나, 찾는 값이 없는 목록으로 바꾸어 확인했다. 사용한 코드에서 정렬이 이루어진 뒤 검색한다는 순서도 함께 점검했다.

| 목록 | 정렬 후 원소 | 42 검색 결과 |
| --- | --- | --- |
| `42, 17, 65, 42` | `17, 42, 42, 65` | `true` |
| 비어 있음 | 비어 있음 | `false` |
| `42` | `42` | `true` |
| `3, 1` | `1, 3` | `false` |

확인한 것은 위 입력에서 예제가 예상대로 동작하는지다. 모든 입력의 정확성이나 표준 알고리즘 전체를 검증한 결과로 확대해서는 안 된다. 테스트할 때는 입력 조건과 기대 결과, 도구가 확인한 범위를 함께 기록한다.

관련 원문 항목은 **P.12, P.13, ES.1, SL.1, SL.2**다. 철학과 표준 라이브러리 장에서 도구와 라이브러리를 활용하는 이유를 설명한다.
