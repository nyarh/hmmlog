# 포스트 작성 규칙

`posts/`의 모든 글을 작성하거나 수정할 때 적용한다.

## 시리즈 파일 관리

- 시리즈 원고는 `posts/series/<시리즈 이름>/` 아래에 회차 순서로 정리한다. 일반 글은 `posts/`에 둔다.
- 시리즈 글의 frontmatter에는 전체 글에서 중복되지 않는 `slug`를 명시한다. 게시 주소는 `/posts/<slug>/`이며, 폴더나 파일명을 바꿀 때도 발행된 `slug`를 유지한다.
- 목차 계획과 검증 기록은 `docs/series/<시리즈 이름>/`에 둔다. 게시하지 않을 문서는 `AGENTS.md`를 제외하고 포스트 폴더에 넣지 않는다.
- 시리즈별 추가 규칙은 해당 원고 폴더의 `AGENTS.md`에 둔다. 이 문서의 공통 규칙과 함께 적용한다.

## 한다체

- 본문은 "한다", "이다", "있다"로 끝나는 한다체를 사용한다.
- 합니다체와 해요체를 섞지 않는다. 직접 인용문과 코드는 원문을 유지한다.
- 제목과 소제목은 내용을 짧게 나타낸다. 명사형을 사용할 수 있다.

## 간결하고 건조한 문체

- 핵심 내용을 먼저 쓰고 필요한 근거와 조건을 설명한다.
- 한 문장에는 한 가지 요점을 담는다. 긴 문장은 의미에 따라 나눈다.
- 사실과 동작을 구체적으로 쓴다. 과장, 감탄, 홍보 표현과 불필요한 수식어를 덜어낸다.
- 독자에게 말을 거는 표현, 수사적 질문, 장식적인 비유를 피한다.
- 형식적인 도입과 마무리, 같은 내용을 반복하는 요약을 삭제한다.
- 이해에 필요한 전제와 예외는 남긴다. 문장을 줄이기 위해 의미를 생략하지 않는다.

## 서두와 예시의 맥락

- 서두에서 글이 다루는 문제나 상황, 설명할 대상을 밝힌다. 구체적인 예시로 시작할 때도 그 예시의 배경을 함께 제시한다.
- 예시의 인자, 값, 단위, 동작을 설명하기 전에 어떤 기능이나 작업에 쓰이는지 소개한다. 작성자가 예시를 알고 있다는 이유로 독자도 그 상황을 안다고 가정하지 않는다.
- 효과나 장점을 설명할 때는 무엇을 어떻게 바꾼 결과인지 알 수 있게 한다. 비교할 상황을 소개하지 않은 채 코드나 오류가 줄어든다는 결론부터 제시하지 않는다.
- 제목이나 이전 회차, 뒤에 나오는 코드만으로 예시의 상황을 추론하게 하지 않는다. 해당 글을 처음 읽는 독자에게 필요한 맥락을 본문에 둔다.
- 간결하게 쓰거나 humanizer로 퇴고할 때도 상황과 대상을 소개하는 설명은 보존한다. 필요한 배경 설명을 형식적인 도입으로 취급해 삭제하지 않는다.

예를 들어 "재시도 횟수와 대기 시간을 모두 같은 정수 타입으로 받으면…"으로 바로 시작하지 않는다. "실패한 작업을 다시 시도하는 함수를 예로 든다. 이 함수는 재시도할 횟수와 각 시도 사이의 대기 시간을 인자로 받는다."처럼 상황과 인자의 역할을 먼저 설명한다.

## 코드 예시

- 코드는 해설에 필요한 범위만 발췌한다. 본문에 싣는 예시가 독립적으로 빌드 가능한 전체 프로그램일 필요는 없다.
- 설명과 무관한 헤더, 진입 함수, 입출력, 실행 준비 코드는 생략한다. 해당 요소가 설명의 주제이거나 동작을 이해하는 데 필요하면 남긴다.
- 코드 조각만으로도 해설의 대상과 동작을 이해할 수 있게 한다. 생략한 부분에 중요한 전제 조건이나 오류 처리가 있다면 필요한 코드나 설명을 남긴다.
- 빌드 명령과 실행 출력은 개념이나 사용 절차를 설명하는 데 필요한 경우에만 싣는다. 본문에 컴파일 확인 여부, 검증 환경, 테스트 목록 등 작성 과정의 기록을 적지 않는다.
- 예제의 정확성은 별도로 검증한다. 검증에 필요한 전체 코드와 컴파일·실행 기록은 본문 밖의 `docs/`에 두며, 시리즈는 해당 시리즈의 문서 폴더를 사용한다.

## humanizer 스킬

- 새 글을 작성하거나 기존 글을 수정한 뒤에는 설치된 humanizer 스킬의 `SKILL.md`를 읽고 적용한다.
- 글 전체를 읽고 반복과 상투적인 표현을 고친다. 수정 전후를 비교해 의미와 정보가 유지되는지 확인한다.
- 퇴고할 때도 한다체와 간결하고 건조한 문체를 유지한다. 경험이나 감정을 지어내지 않는다.
- 사실, 수치, 출처를 보존한다. 문체를 다듬는 과정에서 코드, 명령어, 경로, 링크 주소와 메타데이터를 바꾸지 않는다.
- humanizer 퇴고 후에는 아래의 문맥 검토를 거쳐 원고를 확정한다.

## 퇴고 후 문맥 검토

1. humanizer를 적용한 본문 파일을 처음부터 끝까지 다시 읽는다. 문장별 표현뿐 아니라 글 전체의 설명 흐름을 확인한다.
2. 서두만 따로 읽고 무엇을 다루며 어떤 상황에서 필요한 설명인지 확인한다. 처음 등장하는 예시의 대상과 용어를 그 시점까지 제시한 정보만으로 이해할 수 있어야 한다. 문장 자체의 뜻을 짐작할 수 있어도 예시의 배경이 빠져 있으면 통과시키지 않는다.
3. 문장과 문단 사이의 인과관계, 설명 순서, 주어와 지시어가 가리키는 대상, 용어의 일관성을 점검한다. 새 예시가 등장하는 본문 문단에도 같은 맥락 기준을 적용한다.
4. 어색한 부분은 앞뒤 문맥을 함께 보고 다시 쓴다. 지나치게 줄여 뜻이 모호해졌다면 필요한 설명과 연결 표현을 복원한다. 뒤의 코드나 설명을 읽은 뒤에야 앞 문단을 이해할 수 있다면 필요한 배경을 앞으로 옮긴다.
5. 재수정한 문단과 앞뒤 문단을 다시 읽고, 자연스럽게 이어지는지와 원래 의미·조건이 유지되는지 확인한 뒤 최종 원고에 반영한다.
